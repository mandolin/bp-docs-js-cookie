读取与校验

值没有恢复，或恢复成了意外选项

缺失

首次访问、过期、站点数据被清理

分别回退到 `zh-CN` 与 `system`，再允许访客选择。Cookie 可被提前清除，不是永久数据库。

回到步骤 01
格式异常

未知枚举、截断值或解码失败

只丢弃无效字段并使用默认；不要执行字符串、拼接 HTML 或无限尝试宽松解码。

回到步骤 01
部分状态

语言有效，主题缺失（或相反）

独立校验每个字段，保留有效选择；不要因为一项异常重置全部偏好。

回到步骤 01
并发 / 系统

两个标签页或系统主题产生不同结果

定义入口读取和最后写入策略；js-cookie 本身不提供跨标签事件协议。只有选择 `system` 时跟随系统主题，显式 `light` / `dark` 优先。

回到步骤 02
B

更新与保存

页面改了，但下一次访问没有保留

?
先区分“当前页已应用”和“下次访问可恢复”

当前页应用由应用状态决定；持久化还受过期、scope、HTTPS、浏览器策略和用户清理影响。

浏览器设置阻止写入，应该怎么反馈？

保留本页选择和正文功能；只说明无法确认跨访问恢复，不向用户承诺保存成功，也不尝试绕开浏览器策略。

生产 HTTPS 与本地 HTTP 的结果不同？

生产 HTTPS 明确核对 `Secure`；开发 localhost 的行为单独验证。不要把本地例外外推到真实域名，也不要在示例中放真实 host。

查看步骤 02：更新与保存 →
C

Path / Domain / 迁移

读到旧值、重复值或删不掉

Path 改变

站点从根路径迁到子路径

固定并记录新写入 path；为旧 path 制定迁移/清理步骤。Path 控制发送范围，不是安全边界。

回到步骤 04
子域隔离

不同子域需要共享偏好

本模型默认 host-only。扩大 Domain 前先确认产品需要、所有子域信任边界与删除策略。

回到步骤 00
旧 scope

同名 Cookie 曾在多个 scope 写入

不要假设 `get()` 可以判定具体 path/domain 来源；必须按迁移前记录处理旧 scope。

回到步骤 04
容量 / 驱逐

偏好偶尔消失或存储被回收

只保存短枚举；丢失后回默认。不要把 Cookie 当作大对象存储或永久用户数据库。

回到步骤 03
D

环境与嵌入

代码在浏览器外运行，或页面处于 iframe

SSR / SSG / Node

把浏览器访问放在客户端

构建阶段没有 `document`。服务端确实需要 Cookie 时，使用明确的 request API，不复用浏览器偏好读取来泄露请求值。

第三方 iframe

默认假设存储受限

嵌入上下文可能遇到分区或阻止。CHIPS/Storage Access 需要独立需求和兼容性审查，不等于跨站共享保证。

无 JavaScript

正文与导航仍要可达

无脚本时不宣称 js-cookie 能保存；静态内容、普通链接和基础故障说明仍可读。

同步性能

不要在每次渲染中读取

`document.cookie` 是同步接口；在应用入口读取并校验一次，再使用应用状态。Cookie Store API 是另一条异步路线，需单独做功能检测与 fallback。

浏览器版本也要单独核对

为实际支持的浏览器验证读、写、删除与 HTTPS 属性；本文模型不是浏览器兼容认证，也不承诺 Cookie 永不被驱逐。

E

安全 / 隐私重新定界

用途变成认证、同意或追踪

停止沿用偏好设置路径。

会话/token 应由服务端按认证设计设置 HttpOnly Cookie。SameSite 只是发送条件与部分防护，不能替代敏感写操作的 CSRF 与授权方案。

同意记录、analytics 与广告追踪需要独立的业务用途、隐私负责人决策、字段与保留政策；不能偷偷并入语言/主题流程。登出或切换账户是否保留偏好也要明确；本参考模型按与账户无关处理，认证状态由服务端独立管理。
